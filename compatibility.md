# Mod compatibility contract

The observations below come from the current C# sources in
`/home/ubuntu/vivantvalley_no_langgraph` (the backend design does not change
those files).

## Current outbound requests

### Ordinary dialogue (`ConversationEngine` / `AiProviderClient`)

The Mod posts to the configured endpoint, which is normalized to
`.../chat/completions`, with a bearer credential and JSON like:

```json
{
  "model": "deepseek-v4-flash",
  "messages": [
    {"role": "system", "content": "..."},
    {"role": "user", "content": "..."}
  ],
  "thinking": {"type": "disabled"},
  "reasoning_effort": "low",
  "max_tokens": 2048,
  "stream": false
}
```

For an OpenAI profile, the Mod uses `max_completion_tokens` instead of
`max_tokens` and omits DeepSeek-only `thinking` and `reasoning_effort`.
Messages currently contain only `role` and string `content` in this path.

The normal dialogue UI also uses `stream:true`. It expects `Content-Type:
text/event-stream`, reads lines beginning with `data:`, stops at `data: [DONE]`,
and concatenates `choices[0].delta.content`. DeepSeek reasoning text, when
present, is read from `choices[0].delta.reasoning_content`. A hosted backend
should therefore support SSE forwarding even though non-streaming is the
phase-1 acceptance priority. If streaming is temporarily disabled, return a
documented `400 stream_not_supported` response so the Mod can show a useful
configuration error.

### Tool conversation (`ConversationToolProviderClient`)

The tool client always sends `stream:false`, temperature `0.75`, top-p `0.9`,
and a token cap clamped to 128..2048. The payload adds:

```json
{
  "tools": [
    {
      "type": "function",
      "function": {
        "name": "give_gift",
        "description": "...",
        "parameters": {
          "type": "object",
          "properties": {"candidate_key": {"type": "string"}},
          "required": ["candidate_key"],
          "additionalProperties": false
        }
      }
    }
  ],
  "tool_choice": "auto"
}
```

The Mod builds an allow-listed set of `give_gift`, `move_to`,
`invite_mine_guard`, `invite_fishing_companion`, and always includes
`submit_final_response`. It may force the final function with:

```json
{"type":"function","function":{"name":"submit_final_response"}}
```

The API must preserve tool definitions and choices losslessly while routing
the request to LiteLLM. It must not rename function names or normalize
`function.arguments` into a different type.

## Tool call and tool result message shape

The provider response parser requires `choices[0].message` and accepts text
plus zero or more calls. Each call must contain an ID and a function object:

```json
{
  "id": "call_abc123",
  "type": "function",
  "function": {
    "name": "give_gift",
    "arguments": "{\"candidate_key\":\"salmon\",\"reason_tag\":\"thanks\"}"
  }
}
```

Important protocol details:

- `function.name` is a string and is validated against the current tool
  registry. Unknown tools are rejected before any game side effect.
- `function.arguments` is normally a JSON **string**. The Mod parses that
  string and requires a JSON object. The backend may receive a provider that
  emits an object, but it must serialize the value back as a string when
  forwarding a response to this Mod.
- The assistant message that records a call has `role:"assistant"`, an empty
  or null `content`, and a `tool_calls` array containing `id`, `type` and
  `function`.
- The following tool result has `role:"tool"`, the result text in `content`,
  and the exact matching `tool_call_id`. The Mod uses that ID to correlate the
  game bridge receipt; it must never be regenerated by the gateway.
- The current engine expects at most one action tool call in its action phase,
  then a single `submit_final_response` call in the final phase. The public API
  should preserve multiple calls for general OpenAI compatibility, while the
  Mod-facing policy may reject a response that violates this state machine.

Example assistant and tool messages sent in the finalization request:

```json
[
  {
    "role": "assistant",
    "content": "",
    "tool_calls": [
      {"id":"call_abc123","type":"function",
       "function":{"name":"give_gift","arguments":"{\"candidate_key\":\"salmon\"}"}}
    ]
  },
  {
    "role": "tool",
    "tool_call_id": "call_abc123",
    "content": "{\"ok\":true,\"status\":\"delivered\",\"receipt_id\":\"...\"}"
  }
]
```

## Response shape expected by the Mod

For `stream:false`, return an OpenAI chat completion with at least
`id`, `object:"chat.completion"`, `created`, `model`, `choices[0].index`,
`choices[0].message.role`, `choices[0].message.content` (nullable when only
tool calls are present), `choices[0].message.tool_calls` when applicable, and
`choices[0].finish_reason`. Include `usage.prompt_tokens`,
`usage.completion_tokens`, `usage.total_tokens` and, when known,
`usage.prompt_tokens_details.cached_tokens`.

For `stream:true`, emit standard SSE chunks with `choices[0].delta` and a
final usage-bearing chunk where possible, followed by `data: [DONE]`. Preserve
tool-call deltas (`id`, `index`, `type`, `function.name`, incremental
`function.arguments`) for clients that use streaming tools, even though this
Mod currently uses tools non-streaming.

Errors should be OpenAI-shaped and stable:

```json
{
  "error": {
    "message": "Insufficient balance",
    "type": "billing_error",
    "code": "insufficient_balance",
    "param": null
  }
}
```

The Mod can display HTTP 401/403/429/5xx diagnostics; never include provider
API keys, LiteLLM credentials or full upstream error bodies.

## Model-name migration

The current Mod sends a real provider model such as `deepseek-v4-flash`. The
hosted service intentionally accepts only public aliases (`vv-dialogue`,
`vv-fast`) so routing and cost policy stay server-owned. The Mod integration
must add an "official hosted service" profile whose model defaults to
`vv-dialogue` and whose base URL is the service `/v1`; keep the existing
custom-provider profile for players who supply their own key. During a short
migration window the API may map `deepseek-v4-flash` to `vv-dialogue` for
existing test keys, but this compatibility shim should be disabled before
public launch.

## Context/privacy note

The current tool prompt includes serialized NPC identity, memory summary,
recent messages (up to eight in finalization), scene/activity summaries,
allow-lists, day and location. The API treats all message content and tool
arguments as sensitive and does not persist them by default. The future game
turn endpoint accepts typed context and a server-side conversation ID so these
large fields can be selected and summarized centrally.
